# AI Analysis Sidecar

## Intent

Run opt-in AI analysis against bounded local appliance snapshots without blocking the primary service path.

## When to use this

Use this when an appliance already renders structured local state and an operator wants richer summaries, anomaly notes, or recommendations generated by an external AI API.

## When not to use this

Do not use this when the appliance cannot safely summarize what will leave the device, when generated text must be authoritative, or when the primary control loop would need to wait on the external API.

## System shape

A primary service writes local snapshot files and deterministic fallback state. A separate oneshot worker reads those files, checks opt-in settings and credentials from `/etc/<project>/`, calls a reviewed external AI API, validates the response shape, and atomically writes a local analysis artifact. A timer reruns the worker so missed triggers catch up after downtime.

The worker must be safe to skip. Disabled settings, missing credentials, unchanged snapshots, API errors, schema errors, and rate limits should leave existing deterministic output usable.

- `manifest.yaml` declares the draft pattern contract.

- `examples/minimal/README.md` sketches a minimal implementation.
- `tests/test_manifest.py` provides draft-level test coverage.

## Installation

Adapt the unit names, user, paths, and environment file to the target appliance. Keep API credentials in a root-owned configuration file such as `/etc/<project>/<project>.ai.env`; do not place credentials in unit files.

The timer can be the only trigger for a first implementation. A path unit or request marker can be added later if the primary service needs lower latency and the marker is written atomically.

## Verification

Run `scripts/doctor.sh` and repository validation. In a concrete appliance, prove four cases before enabling live API access:

- disabled settings skip without error.
- missing credentials skip without leaking secrets.
- a mocked valid API response writes the analysis artifact atomically.
- an API or schema failure leaves deterministic local summaries available.

## Failure modes

Expected failures include missing credentials, disabled analysis, stale or missing snapshots, external API timeout, rate limiting, invalid structured output, and write failure for the local analysis artifact. These failures should be visible in local status while preserving the prior good artifact when possible.

## Rollback

Disable and stop the timer and worker, remove copied unit files and helper scripts, and leave existing snapshot and analysis artifacts available for postmortem inspection. Preserve `/etc/<project>` credentials unless an explicit purge operation was requested by the operator.

## Security notes

This pattern creates an intentional network egress path. Treat it as opt-in. Minimize the payload sent to the AI provider, redact secrets, keep credentials outside the repository, and expose generated text as advisory output rather than as an automatic control input. Prefer strict response schemas and deterministic fallback behavior.

## Future work

Future revisions can add a managed installer, a request-marker path unit, provider-specific adapters, cost telemetry, and production-beta lifecycle tests.
